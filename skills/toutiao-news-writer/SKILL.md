# 头条号资讯类图文写作

## 这个 skill 解决什么

用户通常只给一段素材（新闻链接、聊天记录、几张图、一份通稿），却要的是一份**能直接发出去**的头条号图文：标题能点、封面能看、正文读完不累、配图不违规。

头条是信息流产品：标题+封面决定点击，前 100 字决定完读，结尾决定互动。所以不要把它当成“写作文”，要按**三个关卡**分别设计，并且每一关都用素材里的事实兜底。

**产出不是一段文字，而是一个发布包**：`article.md` + `titles.md` + `assets/`（封面与配图）+ `review.md`。

---

## 不可越过的边界

这些不是风格建议，是平台规则与法律风险，违反会让整篇稿子白做：

1. **不编造事实、数据、引语、人物对话。** 素材没有的，就写“暂无公开信息”，或者不写。编造在头条属于“发布谣言或不实内容”，会被限流、扣分、封号。
2. **没有互联网新闻信息服务许可，不写时政/突发/军事/外交/经济政策的“报道与评论”。** 可以改成产业观察、科技科普、生活影响、公开信息整理+个人分析。判断不了就问用户账号资质。
3. **健康、财经的专业结论需要资质。** 不给诊断、用药、买卖建议；只做信息整理并注明“不构成建议”。
4. **图片必须可溯源。** 每张图在 `assets/sources.md` 记录来源与授权；找不到可用来源时，用信息图/AI 示意图，并标注“示意图”。
5. **标题必须在正文里兑现。** 标题给的数字、结论、人物，正文要能一一对应；这是平台“标题与内容不符”的直接红线。
6. **区分事实与观点。** 文末标注信源；故事化写作时明确“个人观点，仅供参考”。

## 工作流

### Step 0 · 读素材，建事实底稿

先把素材拆成可核对的字段，写进 `work/facts.md`：

```
事件：
时间：
地点：
主体：
发生了什么：
关键数字：
直接引语（谁说的）：
信源（媒体/公告/文件/用户口述）：
已确认事实：
待核实：
作者观点：
```

- **文本**：提取 5W1H + 数字 + 引语；标出哪句是媒体转述、哪句是当事人说法。
- **图片**：直接读图，记录画面主体、时间地点线索、是否有水印/其他平台 logo、是否涉及隐私。
- **链接**：抓正文，核对发布时间；旧闻要标年份。
- **用户口述**：视为“单一信源”，标题里不要写成既定事实。

**最后做一次算术核对**：把素材里的百分比、差值、总量互算一遍。比如“峰值 474 万、连续三年减少 131 万、今年约 320 万”——474−131=343，不等于 320，说明这是两个口径。遇到这种情况，**并列写清、标注缺口，不要替用户圆**。数字自洽是资讯稿最容易被读者抓到的破绽。

同时守住每个数字的原始定义：注册 ≠ 报名 ≠ 过审 ≠ 实际参考。差值只能说明“这一层少了多少人”，不能推断“这些人去了哪里、有没有进考场、是不是转去考公”。要推断，必须有另一组数据。

> 为什么先做这一步：后面标题的每个数字都要回到这张表。没有底稿，写着写着就会开始“合理想象”。

### Step 1 · 合规闸门（先判断能不能写）

按 `references/compliance.md` 过一遍，重点看四件事：

| 检查 | 处理 |
|---|---|
| 时政/突发/军事/外交/政策评论 | 无新闻资质 → 换角度或停止，向用户说明 |
| 健康/财经专业建议 | 无资质 → 只做信息整理，加免责声明 |
| 旧闻/时间不明 | 补明确时间，或放弃“最新”叙事 |
| 未证实指控/匿名信源 | 标题不定论，正文标“尚未证实” |

如果素材本身不适合做资讯稿，**先告诉用户原因，再给替代方案**（例如改做“产业链影响”“普通人的三个变化”），不要硬写。

### Step 2 · 选内容类型

| 类型 | 什么时候用 | 字数 | 标题 | 封面 |
|---|---|---|---|---|
| **A 快讯** | 有明确公告/数据/事件，信息量小 | 80–300 | 直陈 5W | 无图或单图现场 |
| **B 汇编** | 多条信息、早报、榜单 | 800–1500 | “N 条/一文看懂” | 大字报/信息图 |
| **C 解读** | 有背景、有因果、有判断 | 1500–2500 | 设问/反差/影响 | 人物或现场 + 图表 |
| **D 故事化** | 有人物命运、有细节、有情绪 | 2000–3000 | 人物+反转+后果 | 人脸特写/强对比 |

选择顺序：**先看信源强度，再看信息量，最后看账号人设**。信源弱却选 D，最容易翻车。

### Step 3 · 标题：10 → 3 → 1

1. 按 `references/title-playbook.md` 的 8 个母题，每个母题至少写 1 条，共 **10 条**。
2. 删到 **3 条**，要求来自不同母题，不要三个都是“设问”。
3. 用 7 问自检，选 **1 条推荐**，并写一句“为什么”。
4. 在 `titles.md` 里标注：母题、字数、正文兑现位置。

标题只做三件事：**让对的人认出领域、制造一个信息缺口、承诺一个收益**。三者缺一，就会出现“看起来还行但没人点”。

资讯类还要多一条：**至少带主体、时间、地点中的一个**。纯反差句（“比 X 更可怕的是 Y”）适合评论，不适合快讯；快讯优先直陈，别让读者猜是谁、什么时候。

### Step 4 · 搭大纲：小标题必须是判断句

输出 4–6 个小标题，每个小标题后面写“证据点”。例如：

```
01 降价不是库存压力，是产能集中释放（证据：三家厂商Q3产能数据）
02 真正被挤压的是二线品牌（证据：渠道商采访/份额表）
03 明年一季度还会有第二轮（证据：历史周期+在建产能）
04 对普通人的影响：现在买还是再等（证据：价保政策/历史价格）
```

如果一个小标题写不出证据点，说明这一段是空的，删掉。

### Step 5 · 写正文

按 `references/structure-playbook.md` 里对应类型的骨架写：

- **开头 60–100 字**：结论 / 数字 / 场景 / 引语，四选一，不要铺垫。
- **250 字内**补全 5W，让读者知道“这事跟我有什么关系”。
- **小标题不是必须的**。短稿可以没有小标题；长稿 2–5 个，节长不要一样，允许一节 150 字、另一节 700 字。
- **每段 1–6 行**，长短交错，不要每段都写成三行。
- **全文 2–3 个真正的转折**（真相、反例、数字、引语），不要每节结尾都敲一次黑板。
- **每 800 字至少一个具体场景、动作或直接引语**，避免通篇都在解释概念。允许有些句子只是事实，不解释、不评价。
- **结尾**停在具体事实、判断或一个真问题；不要默认加“写在最后”。

字数口径：**按正文汉字数算，目标值 ±15%**（后台按字符数统计会更大，交付时在 `word_count` 里写清用的是哪种口径）。用户说“1800 字”，写到 1500–2100 汉字都算达标，不要为凑字注水。

写作时遵守素材边界：事实用陈述句，推测用“可能/大概率/取决于”，观点用“我认为”。

**同时避开 6 个 AI 高频句式**（详见 `references/natural-writing.md`）：

1. 「不是 A，而是 B」——除非 A 是前文已提出的具体事实，否则直接写 B。
2. 「这意味着 / 换句话说」——只在纯复述上一句时删；真引出新推论可以留。
3. 「真正……的是 / 核心在于 / 本质上」——改成具体主语和动作。
4. 「先说结论 / 说白了 / 说到底 / 综上所述」——删引导词。
5. 「在当今……时代 / 随着……的发展」——直接从时间、地点、数字开场。
6. 每段末尾补一句“这才是关键”——删。人不会每段敲一次黑板。

### Step 5.5 · 去 AI 腔（必做，分两层）

初稿写完先别配图，先做一遍清理：

```bash
node scripts/scan-ai-tone.mjs work/draft.md
```

**第一层 · 词句**

- 逐条判断，不要逐条删除：引语、数据、公告原文里的命中跳过。
- 必改 high：翻案腔、起手式、提示语冒号、过长前置定语、“当……时”、话题壳、模糊归因、装饰比喻。
- medium 看语境：这意味着/也就是说只在“纯复述上一句”时删；破折号只在密度超过 2/千字时优先处理。
- 改完再跑一次，**high 清零**才进入下一步。

**第二层 · 结构（这一层比词句更像 AI）**

- 每一节都在 250–500 字？合并一节、拆开一节，或直接删掉一个小标题。
- 每节段数都一样？让其中一节只写一段，另一节写到五段以上。
- 每节结尾都有一句总结/金句？至少删掉两处，让话停在意料之外的地方。
- 有“写在最后/结语”？删掉标题，最后一段直接停在具体事实或一个真问题上。
- 超过三分之一的段落用同两个字开头（“这是/但这/所以”）？换主语、换场景，或直接给数字。
- 连续三句同一个句法骨架？拆掉其中一句，不是删内容。
- 同一段里同一个东西换了三种叫法（优化/提升/增强）？统一回一个词。

**不要做的**（270 对同题配对复测里，这些不是稳定的 AI 信号）：不要为“参差”机械改句长，不要删序数词小标题，不要把所有“这意味着”都删，不要为了像人而硬加“我/你”，不要把每段都改短。

> 为什么单列一步：AI 味不是靠“少用形容词”解决的。它来自**模板化结构 + 每节收束 + 对举句 + 空泛归因 + 同义轮换**。初稿几乎一定会带，必须在配图前清掉。

### Step 6 · 做视觉：封面 + 文中图

先读 `references/visuals.md`。流程：

1. **定封面概念**：写 3 个方案（现场 / 人物 / 信息图），说明各自适配理由，选 1 个。数据型封面至少放 **2 个信息点**（主数字 + 对照数字/时间/范围），只放一个大数字会浪费封面。
2. **选图源**（按优先级）：
   - 用户提供的图片；
   - 官方通稿、政府/企业公告、当事机构发布；
   - 可商用图库、Wikimedia 等明确授权来源；
   - AI 生图（`mmx` 可用时）；
   - HTML 信息图（无 API key 时的默认兜底）。
3. **下载真实图**：
   ```bash
   node scripts/download-image.mjs "<图片URL>" "assets/fig-01.jpg" --source "来源名称 | URL | 授权说明"
   ```
   脚本会把来源追加到 `assets/sources.md`。
4. **渲染封面/信息图**：
   ```bash
   cp assets/cover-lab.html work/cover.html
   # 改 work/cover.html 里的 __KICKER__ / __TITLE__ / __SOURCE__ / __IMAGE__ / __STYLE__
   node scripts/shot.mjs work/cover.html assets/cover.png --size 1280x720
   ```
   `cover-lab.html` 内置 5 种版式：`photo` / `bignum` / `split` / `bulletin` / `stats`。
5. **文中图规划表**（写进 `review.md`）：

   | 位置 | 内容 | 类型 | 来源 | 图注 |
   |---|---|---|---|---|
   | 开头后 | 事件现场 | 现场图 | 官方通稿 | 11月9日，XX现场 |

6. **AI 生图**（可选，检测到才用）：
   ```bash
   mmx image generate --prompt "<画面描述>" --output assets/fig-02.png
   ```
   必须标注“AI 示意图”，且不能用于伪造新闻现场。

### Step 7 · 组装发布包

创建目录（slug 用英文短横线）：

```
<slug>/
├── article.md          # 标题、正文、图注、标签
├── titles.md           # 10 条备选 + 3 条入围 + 推荐理由
├── assets/
│   ├── cover.png
│   ├── fig-01.jpg
│   └── sources.md
└── review.md           # 事实核对、合规检查、AI 腔扫描、配图规划、发布建议
```

`article.md` 用这个结构：

```markdown
---
title: 推荐标题
alternates:
  - 备选标题一
  - 备选标题二
type: C 解读
word_count: 1860
cover: assets/cover.png
tags: [标签1, 标签2, 标签3]
publish_window: "20:00-22:00"
---

![封面](assets/cover.png)

开头段落……

## 01 小标题一

正文……

![图注：谁在什么时间做了什么](assets/fig-01.jpg)

## 02 小标题二

……

（第三节可以只有一段，也可以没有小标题；不要为了整齐补齐四节。）

最后一段停在具体事实、判断或一个没回答的问题上，不需要“写在最后”标题。
```

### Step 8 · 交付前自检

把结果写进 `review.md`，逐项打勾；任何一项不过，先改再交付。

**标题**
- [ ] 有具体主体、冲突/反差、数字/后果中的至少两个
- [ ] ≤28 字，标点 ≤2 个，无极限词/震惊体
- [ ] 正文能逐条兑现标题里的信息
- [ ] 前 10 字含领域关键词

**封面**
- [ ] 缩到 300px 宽，3 秒能看出主体
- [ ] 主体在中间 60% 安全区，文字没贴边
- [ ] 与标题互补，不复述
- [ ] 无其他平台水印/二维码/联系方式

**正文**
- [ ] 前 100 字有钩子，250 字内有 5W
- [ ] 每 300–400 字一个小标题，且是判断句
- [ ] 每个数字都能在 `facts.md` 找到出处
- [ ] 素材里的百分比/差值/总量互算过，对不上的已并列标注
- [ ] 事实/推测/观点三种语气分开
- [ ] 结尾有判断或问题

**合规**
- [ ] 无资质领域已换角度或停止
- [ ] 旧闻已标时间
- [ ] 未证实信息已在正文标注
- [ ] 每张图有来源；AI 图已标“示意图”
- [ ] 文末有信源与免责声明

**人味**
- [ ] `scan-ai-tone.mjs` 的 high 命中已清零
- [ ] 没有未成立的“不是 A，而是 B”
- [ ] 没有“真正 / 核心 / 本质”三件套
- [ ] 没有“在当今 / 随着……的发展”开场
- [ ] 没有装饰性比喻、无出处归因
- [ ] 节长不全部落在 250–500 字，至少有一节明显更长或更短
- [ ] 每节段数不完全相同
- [ ] 没有“写在最后”模板，结尾停在具体事实
- [ ] 至少有一个具体场景、动作或直接引语，不是通篇解释概念
- [ ] 朗读一遍，像人在讲一件事

## 输出时的沟通方式

交付时不要只丢文件，给用户四句话：

1. 我选了什么类型、为什么；
2. 推荐标题是哪个、为什么；
3. 封面用了哪种版式、图从哪来；
4. 有哪些事实需要用户确认（列 1–3 条）。

如果素材不足，直接说“这条缺 X，我有两种处理方式”，不要用模糊表述糊过去。
